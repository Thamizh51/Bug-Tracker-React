End-to-end journey

The core feedback loop

Admin setup enables work; the Tester and Developer roles drive the bug lifecycle.

01 / AdminSet up workspace

Create projects and role-based accounts; assign developer departments.

02 / TesterReport a bug

Select project, describe issue, set priority/team, choose a developer.

03 / DeveloperFix the issue

Review assigned bugs and update status through resolution.

04 / TesterRetest

Check the resolved issue against the expected behavior.

05 / TesterClose or reopen

Close when fixed; reopen when the defect persists.

Rework loop: Reopened bugs return to active project work for another developer pass, then return to tester verification.

Role-based workflows
Who does what

Role workflows

Users sign in with email and password. The application routes them to the dashboard associated with their account role and restricts dashboard routes to that role.

Workspace owner

Administrator

  1. Create and maintain projects.
  2. Set project status: Active, On Hold, Finished, or Archived.
  3. Create accounts with Admin, Developer, or Tester roles.
  4. For Developer accounts, choose Frontend or Backend department.
  5. Review project bugs, user counts, and role-level dashboard summaries.
Operational boundary: Admin can view bug details, but bug assignment or status changes are not exposed in this dashboard.
Quality assurance

Tester

  1. Browse projects and open a project bug list.
  2. Create a bug with title, description, priority, team, and a team-matched developer.
  3. Optionally attach a bug URL and screenshot.
  4. View, edit, or delete reported bugs.
  5. Review resolved bugs, then Close or Reopen after retesting.
Assignment rule: Changing Frontend/Backend filters the developer choices and clears the previous selection.
Engineering delivery

Developer

  1. Review bugs assigned to the signed-in developer.
  2. Search and filter assigned or project bugs by status and priority.
  3. Open details, including description, links, and screenshots.
  4. Update status to Pending, In Progress, or Resolved.
  5. Return resolved work to the tester retest queue.
Ownership: Assignment is made from the tester bug form; developer dashboard actions focus on status and review.
Shared experience

Cross-role behavior

  1. Role is taken from the authenticated user record.
  2. Session token is used for API requests.
  3. Logout calls the API and clears local session data.
  4. Bug/project lists provide search, filters, summaries, and detail views.
System dependency: The frontend calls a separate API service at the configured API base URL.

Product capabilities in the current UI

  • Project lifecycle management and status controls.
  • User creation across three roles; developer department capture.
  • Bug intake with priority, team, developer assignment, URL, and image.
  • Search/filter bug lists and inspect full bug details.
  • Developer status updates and tester close/reopen retest outcomes.

Decisions / gaps for product review

  • User editing: UI exposes Edit, but the frontend reports that the update API is not implemented.
  • Assignment governance: Tester currently chooses the developer at intake; confirm whether reassignment should be available later.
  • Status ownership: Developer and tester transitions are role-specific; confirm permitted transitions and audit requirements.
  • Notifications: No in-app/email notification flow is visible in the frontend.
  • Project visibility: Confirm whether archived/finished projects should remain selectable for new bug reports.

Suggested acceptance checks

Each bug has one identifiable project, priority, team, and assignee; only developers in the selected team can be assigned. A resolved bug appears in retest. Close removes it from retest; Reopen returns it to active work. Role-restricted routes do not expose another role's dashboard.

Scope: Frontend implementation reviewed 03 October 2026; confirm backend rules with the API owner.
